# APExp 0.7 (in development)

0.6 is tagged. This file is the plan and the running state; the history
of each item goes to its topic file under `docs/notes/` as usual, and
only the one-line consequence comes back to `CLAUDE.md`.

**The open-bug inventory for 0.6 stays in `docs/releases/0.6.md`.**
Anything that moves out of it moves into this file with the measurement
beside it.

---

## The list

1. **The archivers** — two decode failures, neither separated.
2. **go and clisp** — finish the ports, and test them; chicken too.
3. **Cross-compilation** — `$cputype` against `$objtype`, starting with
   386.
4. **portable_stl** — how to install it, and whether the namespace can
   be renamed.
5. **A proof-of-concept C++/STL application** — a modern unrar, or
   tkdesk.

What follows is the state of each. **Three of the five already have a
measurement or a settled answer**, and two of those came from reading
the tree rather than from the VM.

## 1. The archivers

**The hangs are closed.** Both were libap's `pthread_create`, and the
refutation condition written down before the run did not fire: lz4 was
wedged on the same mechanism via `programs/threadpool.c`. `fsync`
answering failure, which made `xz` delete every file it wrote, is fixed
behind it. `docs/notes/libap.md` has the two `acid` stacks.

**What is left is two decode failures, and the reason they are still
one item rather than two is that neither is separated:**

```
unxz xz_sample_file_1MB.xz   -> Compressed data is corrupt
unlz4 sample.txt.lz4         -> Error 26 : LZ4F frame decoding could
                                not complete: invalid frame
                                Decompressed : 0 MiB
```

**Both files were produced elsewhere**, so each has two explanations —
a bad download, or a path only those files reach — and *nothing local
has been round-tripped to tell them apart*.

***The positive result is hidden inside the sync error.*** `unxz
/tmp/t.xz` reached `io_sync_dest`, which runs **after** decoding, so
encoder and decoder already agree on a small file. That is the first
end-to-end xz round trip this tree has had, and it arrived disguised as
a failure.

**Two runs separate everything:**

- A local round trip at size: build ~1MB, `xz -c <big >/tmp/big.xz`,
  `xz -dc /tmp/big.xz | cmp - big`, and read `echo $?` rather than
  trusting silence. Clean means the downloads are the suspect.
- `-T1` against the default `-T0`. **xz defaults to threads = cores,
  and the threaded encoder is ground nothing in this tree has ever
  covered**, because until 0.6 no thread ever reached its start
  routine. *A fix that makes a process reach code it never reached
  before can expose anything on that path* — so if `-T1` round-trips
  and `-T0` does not, that is a new bug and not an old one.

Same shape for lz4: `lz4 -c sample.txt >/tmp/s.lz4 && unlz4 -c
/tmp/s.lz4`.

**Untried**: zstd (same position — `lib/common/pool.c` uses pthreads),
unrar, unace, clzip. `unarj` lists a 1MB archive correctly.

**First, though: `fsync` has not actually been measured.** `fsync-test`
printed nothing on its first run, and in the same session `unxz` still
deleted its output — so that build did not contain the fix. `mk
distclean` before anything in this section, since `mk install` rebuilds
`libap.a` without relinking binaries already built against it.

## 2. go, clisp, chicken

**go** stopped four times, each one file further in, and all four were
this tree's own mkfile rather than go. The fourth is the structural one:
`cmd/dist` is compiled `-DPLAN9`, which selects `plan9.c` and its
`<u.h>`/`<libc.h>` under a compiler that has neither. **The portable arm
is already written and switched off** — `unix.c` is 843 lines of POSIX
and every one of its nine includes exists here. The macro is doing two
unrelated jobs, which is the thing to separate.

**clisp** reaches `C compiler cannot create executables` with hundreds
of `5: Bad file descriptor` around it. **That verdict is a configure
that could not write its own log**, not a statement about `pcc` — the fd
mechanism is cleared (`execfd-test.sh`, 11 sections, 0 failures,
self-re-exec and 300 forks included). The plan is a hand-answered
`config.h` plus an mkfile, as perl and bash already have.
`mkfile.runtime` has an `ARCHDEF` conditional with **only an amd64 arm**,
which item 3 will need to widen.

**chicken** builds, and both compiler bugs it found are fixed and
measured (`longconst-test`, `switchcase-test`, both 0). What is left is
running `chickenword-probe` with chicken's own flags. *A port that
builds is not a port that works*, which is the gap all three share.

## 3. Cross-compilation: `$cputype` against `$objtype`

**The suspicion was right and the direction was the other way round.**

The rule is mechanical: `$objtype` is **what you compile for**,
`$cputype` is **what you run on**. So headers and libraries take
`$objtype` — they are compiled *against* — and binaries take `$cputype`,
because they are *executed*.

Audited, and two of the three were already correct:

| file | verdict |
|---|---|
| `sys/src/ape/config` | correct — `APEBIN=/$objtype/bin/ape`, and `< /$objtype/mkfile` picks the target's `$O`/`CC` |
| `apexp-sh` | correct — binds `$cputype/bin` and `$cputype/bin/ape`, which is what you run |
| `mount-include` | **wrong, and fixed** — it bound the *target's* headers and libraries using `$cputype` |

With `$cputype` in `mount-include`, `objtype=386 mk install` on an amd64
machine binds amd64's `float.h`, `stdarg.h`, `stdint.h` and
`stddef_arch.h` into place, while pcc searches `/386/include/ape` —
which the script never touched. **So the build quietly reads stock
9front's 386 headers, or fails to find APExp's, and neither of those
says "wrong architecture" anywhere in the message.** The change is a
no-op on every build anyone has run, because the tree has only ever been
built on amd64 for amd64.

**Hardcoding is not the problem.** A grep for `amd64`, `6c`, `6l` and
`6a` across every mkfile in `sys/src/ape` finds exactly two non-comment
hits, and both are deliberate: clisp's `if (~ $objtype amd64)` and
`lib/ap/mp/mkfile`'s test recipe.

### The blocker that comes first: `stddef_arch.h` exists for three
### architectures out of eleven

```
386  NO   68020 NO   amd64 yes  arm   NO   arm64 yes  mips NO
power NO  power64 yes sparc NO  sparc64 NO  spim NO
```

`<stddef.h>` includes `<stddef_arch.h>` **unconditionally**, and so do
`<sys/types.h>`, `<limits_generic.h>` and `<stdint_generic.h>`. So a
missing copy is not a fallback — **it is a failure at the first
`#include <stddef.h>` in the first file compiled.** `386` has one now;
it defines `_ptrdiff_t` and nothing else, because 386 is ILP32 and
`<stddef.h>`'s own `#ifndef _SIZE_T` arm is already right there. *The
header exists at all for the 64-bit targets*, which are LLP64 under
kencc and need `size_t` forced to 64 bits ahead of that arm.

**The other seven are left out deliberately rather than written blind.**
Five of them plus spim want exactly the 386 file; **sparc64 is 64-bit
and wants amd64's**, which is a different file. And a cross build stops
at the first thing missing, so there will be more than this — *the next
one should be found by a build rather than guessed by a reader.* Note
`sparc`, `sparc64` and `spim` carry 7, 7 and 8 tracked files against
386's 12, so they are further behind than the table above shows.

### FIRST MEASUREMENT: `objtype=386 mk install` stops on the fourth command

```
8c -FTVw ar.c
ar.c:586 bad in naddr: REGPAIR
ar.c:586 bad in naddr: REGPAIR
mk: 8c -FTVw ar.c : exit status=8c 332996: error
```

**It got past `mount-include` and into `sys/src/cmd`**, which is the
part that was in doubt — the namespace is right and `8c` is being
selected, so items above this one did their job. What it stopped on is
something else entirely.

`ar.c:586` is `as->offset = ap->size;`, and **both members are
`vlong`** — a plain 64-bit member-to-member assignment, in a file this
tree has never touched (`sys/src/cmd/ar.c` has one commit, the import).

***Why amd64 could never have shown it.*** `OREGPAIR` is how 8c holds a
64-bit value in two 32-bit registers, and a grep finds it in `8c/` and
`cc/pswt.c` and **nowhere else**. The entire 64-bit code generator,
`8c/cgen64.c`, is 8c's alone — 6c does not need one, since a vlong is a
single amd64 register. **So the 386 backend's 64-bit path is exactly
the part of kencc that every build this tree has ever done was unable
to reach.** *This is the general shape to expect from the whole
cross-compilation item, not a one-off.*

**IT IS OURS, AND THAT IS MEASURED.** Stock `8c`, run from a plain
`term%` window where `/bin` is 9front's own, compiles this very `ar.c`
and leaves an `ar.8` behind — and the whole of `/sys/src` cross
compiles to 386 on the host. APExp's `8c` fails on the same file.
*The input is identical, so the difference is the compiler.*

***AND `git bisect` CANNOT REACH IT. I said the opposite above and it
was wrong.*** The thirteen commits under `sys/src/cmd/cc/` are **not**
the delta from stock: this repository's **root commit already contains
`isbool`, `vlasizevar`, `alignas_req`, `_Generic` and VLA**, so the
import is APExp's compilers at an advanced state rather than 9front's.
*Every kencc patch older than the repository is invisible to the
history and is exactly as likely to be the cause.* A bisect would have
run to the root and reported "it was always broken", which is a wrong
answer that looks like a result.

**So the instrument is a source diff against the running system**, and
it can only be taken on the VM:

```
diff -r /sys/src/cmd/cc $home/APExp/sys/src/cmd/cc
diff -r /sys/src/cmd/8c $home/APExp/sys/src/cmd/8c
```

*(And those are trustworthy now in a way they were not a month ago —
the `st_rdev` fix is what stopped `diff` calling two different files
identical.)*

**One build then splits the search in half.** APExp's `8c/` uses names
only APExp's `cc.h` defines — `conformalign`, `talign`, `dupokall` — so
stock-`cc` with APExp-`8c` will not compile. The other pairing will,
because stock `8c/` asks for nothing new. So build `8c` from **APExp's
`cc/` and stock `8c/`**, and compile `ar.c` with it:

- it **fails** → the fault is in the shared front end, `cc/`;
- it **passes** → the fault is in `8c/` itself, which would be a
  surprise worth having: the only changes this repository made there
  are `-J`'s and `-C`'s, and both sit behind flags this compile does
  not pass.

`sys/lib/tests/regpair-probe.c` narrows the construct, and the first
run covered **all ten backends**:

```
6c amd64   COMPILES     7c arm64   COMPILES
9c power64 COMPILES     kc sparc64 COMPILES

8c 386     case 1
5c arm     case 2's parameter, case 2's return
qc power   case 2's return
1c 68000   cases 1,2,3,4,5,6 -- and `too many errors'
2c 68020   the same set
```

**Every 64-bit backend passes and every 32-bit backend fails** — which
is what a path only a register *pair* can reach looks like, and it says
the four that pass prove nothing about the four that fail.

***They are not one bug.*** 5c and qc fail on *returning* a vlong,
which 8c compiles; 8c fails on case 1, which 5c and qc compile; 1c and
2c fail on everything, which reads as no vlong support rather than a
defect in it. **So "the 32-bit backends are broken" is a summary and
not a diagnosis, and this item is at least three pieces of work.**

**8c's result is the sharpest thing in the run: case 1 and nothing
else** — not the parameter, not the return, not the 32-to-64 widening,
not `d->offset = d->offset + 1`, not the vararg. Its 64-bit support is
broadly working and exactly one shape is not: *the shape `ar.c:586`
uses*. Cases 7–11 split that shape along its three seams — how many
indirections, whether the two structs share a type, and whether load
and store are one expression. **If case 8 (the same work in two
statements through a local) compiles where case 1 does not, the fault
is holding two register pairs live at once — the register allocator,
not the shared front end.**

**Stock `8c` compiles `regpair-probe.c` and leaves a `regpair-probe.8`.**
So both halves are now measured and they agree:

| | `ar.c` | `regpair-probe.c` |
|---|---|---|
| stock `8c` | compiles | compiles |
| APExp `8c` | fails at 586 | fails at case 1 |

***It is a regression, and the probe is a faithful reduction of it.***
Three lines reproduce what stopped the cross build, which is what makes
the rest of this tractable: the thing to look for now is a change that
breaks `d->offset = s->size` on a 32-bit target and nothing else.

### The prediction for cases 7–11, written before the run

*This belongs here rather than in the probe's header, because editing
that header is what moved the line numbers last time.* 8c fails on case
1 alone — not the parameter, the return, the widening, the
single-pointer self-assignment or the vararg.

- **A — two register pairs live at once** (the allocator, not the front
  end): **case 7 FAILS** (same type, still two indirections) and **case
  8 passes** (the same work split into two statements, one pair at a
  time). 9, 10 and 11 pass.
- **B — something about the two struct TYPES differing**: case 7
  **passes**, case 8 passes, 9/10/11 pass.

**A is the one I expect**, because case 5 (`d->offset = d->offset + 1`)
already compiles and it has the same type on both sides.

**What refutes both**: any of 9, 10 or 11 failing. Those have one
indirection or none, and cases 3 and 5 already compile with one — so a
failure there would mean the shape is not about indirection count at
all, and this whole reading is wrong.

### What unblocks the search

**`diff -r /sys/src/cmd/cc $home/APExp/sys/src/cmd/cc`** on the VM, and
the same for `8c`. The repository's history cannot supply it — the root
commit is already APExp's compilers well advanced — so this diff is the
only full statement of what we changed, and it is one command.

### The shape to expect after that

**A recipe that runs a binary it just built cannot cross-compile**, and
the tree has two outside `mk test`: `cmd/perl/mkfile:86` (`./miniperl`
generates `perlmain.c`) and `cmd/muon/mkfile:192` (`./embedder`). Each
needs a host build of that one tool, or a checked-in generated file.
libressl's `test/mkfile` runs several, but only under `mk test`.

## 4. portable_stl

**Both questions are answered from the source, and both answers are
no.**

### There is nothing to build and nothing to install

`CMakeLists.txt` has **no `install()` rule and no `configure_file`**.
Its single target is `add_executable(portable_stl unit_test/...)` — the
gtest suite — and it fetches Hunter and GTest from the network to build
it. So "nothing changes in the headers" is exactly right: *the headers
are the product.* `cmake .. && make` builds the test binary and nothing
else.

**So installation is a copy**, and `sys/include/ape/pstl` is a
reasonable home. The one thing to decide is whether anything in the
tree should see it without asking — it should not, which an
`-I$APEXPROOT/sys/include/ape/pstl` in the consuming mkfile gives and a
default search path does not.

### The namespace cannot become `std`, and `portable_stl` is not just
### conflict avoidance

`namespace portable_stl` is spelled out **1283 times** across the
headers, with nested helper namespaces inside it, so it is not a single
`#define` point. That is the weak reason. The strong one:

> `include/portable_stl/language_support/initializer_list_stl/initializer_list.h:15`
> `namespace std {`
> `include/portable_stl/language_support/typeinfo/type_info_stl/type_info.h:18`
> `namespace std {`

**The library already uses `namespace std` itself**, for the two things
the *core language* requires to live there: `std::initializer_list`,
which every braced-init-list resolves against, and `std::type_info`,
which `typeid` returns. A `namespace std = portable_stl;` would collide
head-on with its own declarations. *`std::` is not free here; it is
occupied on purpose.*

**And renaming would not buy compatibility anyway**, which is the part
worth stating plainly rather than discovering in a port:

```cpp
::portable_stl::expected<void, ::portable_stl::portable_stl_error>
push_back(const_reference value);
```

`vector::push_back` returns `expected<void, portable_stl_error>`, not
`void`. **The library is exception-free by construction** — that is what
it is *for*, which is also why it suits a toolchain with no exception
runtime — so every fallible operation returns `expected`. Code written
against the real `<vector>` does not compile against it whatever the
namespace is called. ***It is a conformance corpus and a usable library,
but it is not a drop-in `std`.***

## 5. A proof-of-concept C++ application

Two candidates, and they ask different questions:

- **a modern unrar** — C++ since 2.71, which is why the tree ships the
  last pure-C version. It would be the first real test of the EDG
  pipeline on somebody else's C++, and it needs an STL.
- **tkdesk** — its mkfile is in `sys/src/ape/app` and it is **not built
  by default**, being a proof of concept rather than part of APExp. It
  is C, so it proves itcl/Tk rather than C++; the bonus is that it is
  the first real itcl/Tk application here. (`tkblt` was dropped: 3.2 is
  C++ with namespaces, and tkdesk never needed it — it ships its own BLT
  subset in C.)

**What the C++ one has to clear first** is in `docs/notes/edg.md`: the
static-init gap (nothing calls `_Z12__call_ctorsv`), `__thread` silently
dropped, and `--instantiate local`'s own cost — internal linkage gives
each object its own copy, so a template's static data member stops being
one object shared across the program. *A program whose correctness rests
on that identity is silently wrong rather than loudly broken, and one
translation unit cannot show it.*
