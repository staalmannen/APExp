## 1. The archivers

**The hangs are closed.** Both were libap's `pthread_create`, and the
refutation condition written down before the run did not fire: lz4 was
wedged on the same mechanism via `programs/threadpool.c`. `fsync`
answering failure, which made `xz` delete every file it wrote, is fixed
behind it. `docs/notes/libap.md` has the two `acid` stacks.

**What is left is two decode failures, and the reason they are still
one item rather than two is that neither is separated:**

```
unxz xz_sample_file_1MB.xz   -> Compressed data is corrupt
unlz4 sample.txt.lz4         -> Error 26 : LZ4F frame decoding could
                                not complete: invalid frame
                                Decompressed : 0 MiB
```

**Both files were produced elsewhere**, so each has two explanations —
a bad download, or a path only those files reach — and *nothing local
has been round-tripped to tell them apart*.

***The positive result is hidden inside the sync error.*** `unxz
/tmp/t.xz` reached `io_sync_dest`, which runs **after** decoding, so
encoder and decoder already agree on a small file. That is the first
end-to-end xz round trip this tree has had, and it arrived disguised as
a failure.

**Two runs separate everything:**

- A local round trip at size: build ~1MB, `xz -c <big >/tmp/big.xz`,
  `xz -dc /tmp/big.xz | cmp - big`, and read `echo $?` rather than
  trusting silence. Clean means the downloads are the suspect.
- `-T1` against the default `-T0`. **xz defaults to threads = cores,
  and the threaded encoder is ground nothing in this tree has ever
  covered**, because until 0.6 no thread ever reached its start
  routine. *A fix that makes a process reach code it never reached
  before can expose anything on that path* — so if `-T1` round-trips
  and `-T0` does not, that is a new bug and not an old one.

Same shape for lz4: `lz4 -c sample.txt >/tmp/s.lz4 && unlz4 -c
/tmp/s.lz4`.

**Untried**: zstd (same position — `lib/common/pool.c` uses pthreads),
unrar, unace, clzip. `unarj` lists a 1MB archive correctly.

**First, though: `fsync` has not actually been measured.** `fsync-test`
printed nothing on its first run, and in the same session `unxz` still
deleted its output — so that build did not contain the fix. `mk
distclean` before anything in this section, since `mk install` rebuilds
`libap.a` without relinking binaries already built against it.

## 3. Cross-compilation: `$cputype` against `$objtype`

**The suspicion was right and the direction was the other way round.**

The rule is mechanical: `$objtype` is **what you compile for**,
`$cputype` is **what you run on**. So headers and libraries take
`$objtype` — they are compiled *against* — and binaries take `$cputype`,
because they are *executed*.

Audited, and two of the three were already correct:

| file | verdict |
|---|---|
| `sys/src/ape/config` | correct — `APEBIN=/$objtype/bin/ape`, and `< /$objtype/mkfile` picks the target's `$O`/`CC` |
| `apexp-sh` | correct — binds `$cputype/bin` and `$cputype/bin/ape`, which is what you run |
| `mount-include` | **wrong, and fixed** — it bound the *target's* headers and libraries using `$cputype` |

With `$cputype` in `mount-include`, `objtype=386 mk install` on an amd64
machine binds amd64's `float.h`, `stdarg.h`, `stdint.h` and
`stddef_arch.h` into place, while pcc searches `/386/include/ape` —
which the script never touched. **So the build quietly reads stock
9front's 386 headers, or fails to find APExp's, and neither of those
says "wrong architecture" anywhere in the message.** The change is a
no-op on every build anyone has run, because the tree has only ever been
built on amd64 for amd64.

**Hardcoding is not the problem.** A grep for `amd64`, `6c`, `6l` and
`6a` across every mkfile in `sys/src/ape` finds exactly two non-comment
hits, and both are deliberate: clisp's `if (~ $objtype amd64)` and
`lib/ap/mp/mkfile`'s test recipe.

### The blocker that comes first: `stddef_arch.h` exists for three
### architectures out of eleven

```
386  NO   68020 NO   amd64 yes  arm   NO   arm64 yes  mips NO
power NO  power64 yes sparc NO  sparc64 NO  spim NO
```

`<stddef.h>` includes `<stddef_arch.h>` **unconditionally**, and so do
`<sys/types.h>`, `<limits_generic.h>` and `<stdint_generic.h>`. So a
missing copy is not a fallback — **it is a failure at the first
`#include <stddef.h>` in the first file compiled.** `386` has one now;
it defines `_ptrdiff_t` and nothing else, because 386 is ILP32 and
`<stddef.h>`'s own `#ifndef _SIZE_T` arm is already right there. *The
header exists at all for the 64-bit targets*, which are LLP64 under
kencc and need `size_t` forced to 64 bits ahead of that arm.

**The other seven are left out deliberately rather than written blind.**
Five of them plus spim want exactly the 386 file; **sparc64 is 64-bit
and wants amd64's**, which is a different file. And a cross build stops
at the first thing missing, so there will be more than this — *the next
one should be found by a build rather than guessed by a reader.* Note
`sparc`, `sparc64` and `spim` carry 7, 7 and 8 tracked files against
386's 12, so they are further behind than the table above shows.

### FIRST MEASUREMENT: `objtype=386 mk install` stops on the fourth command

```
8c -FTVw ar.c
ar.c:586 bad in naddr: REGPAIR
ar.c:586 bad in naddr: REGPAIR
mk: 8c -FTVw ar.c : exit status=8c 332996: error
```

**It got past `mount-include` and into `sys/src/cmd`**, which is the
part that was in doubt — the namespace is right and `8c` is being
selected, so items above this one did their job. What it stopped on is
something else entirely.

`ar.c:586` is `as->offset = ap->size;`, and **both members are
`vlong`** — a plain 64-bit member-to-member assignment, in a file this
tree has never touched (`sys/src/cmd/ar.c` has one commit, the import).

***Why amd64 could never have shown it.*** `OREGPAIR` is how 8c holds a
64-bit value in two 32-bit registers, and a grep finds it in `8c/` and
`cc/pswt.c` and **nowhere else**. The entire 64-bit code generator,
`8c/cgen64.c`, is 8c's alone — 6c does not need one, since a vlong is a
single amd64 register. **So the 386 backend's 64-bit path is exactly
the part of kencc that every build this tree has ever done was unable
to reach.** *This is the general shape to expect from the whole
cross-compilation item, not a one-off.*

**IT IS OURS, AND THAT IS MEASURED.** Stock `8c`, run from a plain
`term%` window where `/bin` is 9front's own, compiles this very `ar.c`
and leaves an `ar.8` behind — and the whole of `/sys/src` cross
compiles to 386 on the host. APExp's `8c` fails on the same file.
*The input is identical, so the difference is the compiler.*

***AND `git bisect` CANNOT REACH IT. I said the opposite above and it
was wrong.*** The thirteen commits under `sys/src/cmd/cc/` are **not**
the delta from stock: this repository's **root commit already contains
`isbool`, `vlasizevar`, `alignas_req`, `_Generic` and VLA**, so the
import is APExp's compilers at an advanced state rather than 9front's.
*Every kencc patch older than the repository is invisible to the
history and is exactly as likely to be the cause.* A bisect would have
run to the root and reported "it was always broken", which is a wrong
answer that looks like a result.

**So the instrument is a source diff against the running system**, and
it can only be taken on the VM:

```
diff -r /sys/src/cmd/cc $home/APExp/sys/src/cmd/cc
diff -r /sys/src/cmd/8c $home/APExp/sys/src/cmd/8c
```

*(And those are trustworthy now in a way they were not a month ago —
the `st_rdev` fix is what stopped `diff` calling two different files
identical.)*

**One build then splits the search in half.** APExp's `8c/` uses names
only APExp's `cc.h` defines — `conformalign`, `talign`, `dupokall` — so
stock-`cc` with APExp-`8c` will not compile. The other pairing will,
because stock `8c/` asks for nothing new. So build `8c` from **APExp's
`cc/` and stock `8c/`**, and compile `ar.c` with it:

- it **fails** → the fault is in the shared front end, `cc/`;
- it **passes** → the fault is in `8c/` itself, which would be a
  surprise worth having: the only changes this repository made there
  are `-J`'s and `-C`'s, and both sit behind flags this compile does
  not pass.

`sys/lib/tests/regpair-probe.c` narrows the construct, and the first
run covered **all ten backends**:

```
6c amd64   COMPILES     7c arm64   COMPILES
9c power64 COMPILES     kc sparc64 COMPILES

8c 386     case 1
5c arm     case 2's parameter, case 2's return
qc power   case 2's return
1c 68000   cases 1,2,3,4,5,6 -- and `too many errors'
2c 68020   the same set
```

**Every 64-bit backend passes and every 32-bit backend fails** — which
is what a path only a register *pair* can reach looks like, and it says
the four that pass prove nothing about the four that fail.

***They are not one bug.*** 5c and qc fail on *returning* a vlong,
which 8c compiles; 8c fails on case 1, which 5c and qc compile; 1c and
2c fail on everything, which reads as no vlong support rather than a
defect in it. **So "the 32-bit backends are broken" is a summary and
not a diagnosis, and this item is at least three pieces of work.**

**8c's result is the sharpest thing in the run: case 1 and nothing
else** — not the parameter, not the return, not the 32-to-64 widening,
not `d->offset = d->offset + 1`, not the vararg. Its 64-bit support is
broadly working and exactly one shape is not: *the shape `ar.c:586`
uses*. Cases 7–11 split that shape along its three seams — how many
indirections, whether the two structs share a type, and whether load
and store are one expression. **If case 8 (the same work in two
statements through a local) compiles where case 1 does not, the fault
is holding two register pairs live at once — the register allocator,
not the shared front end.**

**Stock `8c` compiles `regpair-probe.c` and leaves a `regpair-probe.8`.**
So both halves are now measured and they agree:

| | `ar.c` | `regpair-probe.c` |
|---|---|---|
| stock `8c` | compiles | compiles |
| APExp `8c` | fails at 586 | fails at case 1 |

***It is a regression, and the probe is a faithful reduction of it.***
Three lines reproduce what stopped the cross build, which is what makes
the rest of this tractable: the thing to look for now is a change that
breaks `d->offset = s->size` on a 32-bit target and nothing else.

### The prediction was made and A was refuted; B holds

Written before the run: **A** (two register pairs live at once — the
allocator) predicted **case 7 would fail**; **B** (something about the
two struct *types* differing) predicted case 7 would pass.

```
bash-5.3$ 8c regpair-probe.c
regpair-probe.c:181 bad in naddr: REGPAIR
regpair-probe.c:181 bad in naddr: REGPAIR
```

**181 is case 1, and nothing else is named.** So cases 7, 8, 9, 10 and
11 all compile:

- **case 7 passes** — `d->offset = e->offset` through two `Dst *`. Two
  indirections, two base pointers, one register pair. ***A is
  refuted***: register pressure is identical to case 1 and it compiles.
- case 8 passes, which under A would have been the *confirming* result
  and under B is just a consequence.
- 9, 10 and 11 pass, so the **refutation condition for both hypotheses
  did not fire** and the reading is still about indirection shape.

***The discriminator is that the two structs are DIFFERENT TYPES.***
`Dst *` to `Dst *` is fine; `Dst *` to `Src *` is not. That is a much
smaller target than "the 64-bit path", and it points at the type
machinery in the shared front end rather than at the register
allocator.

**`tcopy` is not it, and that is checked rather than assumed**: it is
untouched by this tree, and it returns `t` unchanged for scalars whose
link has not moved — so `Dst.offset` and `Src.size` are the *same*
`types[TVLONG]` object. The member types are identical; it is the
enclosing types that differ.

### Cases 12–14, and the prediction for them

`Src` differs from `Dst` in **three** ways at once, which is a fault in
the original reduction: no self-pointer, eight bytes shorter, and a
differently named member. So:

- **12** — `Twin`, exactly `Dst`'s layout under another tag:
  self-referential, same width, member also called `offset`.
- **13** — `Plain`, `Src`'s layout with `Dst`'s member *name*: not
  self-referential, shorter, member called `offset`.
- **14** — case 1 backwards, `s->size = d->offset`.

**Predicted:** if the mere difference of **tag** is enough, 12 and 13
both fail. If **layout or the self-pointer** is what matters, 12 passes
and 13 fails. If 12 and 13 both *pass*, then the member **name** is
implicated, which would be surprising enough to be worth knowing.
**14 asks whether direction matters** — a failure one way only puts the
fault in the store or the load rather than in the pair of types.

*The prediction lives here and not in the probe's header, because
editing that header is what moved the measured line numbers before.*


### The diffs arrived, and they say something I had not allowed for

`tmp/cc.diff` (3768 lines) and `tmp/8c.diff` (434) are on `main`.
**The first thing in them is not a bug, it is a correction to how I was
reading the whole problem:**

```
<  typedef	struct	Spec	Spec;          <- /sys/src/cmd/cc  (stock)
<  int	simpleg(Spec);
>  int	simpleg(long b);                  <- APExp
```

`Spec` does not exist anywhere in APExp's `cc.h`. **So APExp's
compilers are forked from an OLDER 9front**, and a large part of that
3768-line diff is *9front moving forward*, not our patches.

***Which means "stock compiles it, ours does not" does not establish
that we broke it.*** It establishes that the two compilers differ.
The cause may just as well be **an upstream fix our older base lacks**.
I called it "a regression" and meant "ours"; the measurement only
supports "theirs works and ours does not". Separating those needs
9front's own history, which neither the diff nor this repository has.

*This is the second time the attribution has been wrong in the same
direction* — first the git history was taken for the delta from stock,
now the source diff was taken for our patch set.

**What the 8c diff does contain**, read in full since it is short:

- `OALLOCA` — VLA support, a new `case` in `cgen`.
- **`nodrat` → `regsalloc` at four sites**, plus the deletion of
  `if(nn == nodrat) if(w > nrathole) nrathole = w;`. One of those four
  is `cgen.c`'s `case ODOT`, which is the `.`/`->` path. *Whether that
  is our patch or their later change, the diff cannot say.*
- `true` → `cond`/`vcond` throughout, which is ours: `true` became a
  keyword.

And in `cc/sub.c`: complex widths, `ptrsignonly` (the `-Wpointer-sign`
warning), and the `Spec`/`long` signature difference above. **Nothing
on the path from a `vlong` member to another `vlong` member.**

### The instrument that makes attribution unnecessary

`8c/txt.c`'s `naddr` has carried a commented-out `prtree(n, "naddr")`
one line under the diagnostic for as long as the file has existed.
**It is uncommented now.**

`bad in naddr: REGPAIR` names the victim, not the cause: it says a
64-bit value arrived somewhere that can only take an address, and says
nothing about which expression or how it got there. **Four rounds went
into reducing `ar.c` to three lines by hand when the compiler could
have printed the shape itself.**

It is unconditional rather than behind a debug letter, deliberately:
this arm only runs when the compile has *already failed*, so there is
no output to spam — and a new debug letter is the trap this tree fell
into once already, since `ARGBEGIN`'s default arm swallows any unknown
letter (which is why `-J` is not `-P`).

**Rebuild 8c and run it on the probe.** The tree it prints for case 1,
set beside case 7's silence, says what the shape is — and then the fix
is the same work whether the hunk is ours or 9front's.

### The tree printed, and BOTH hypotheses are dead

```
bash-5.3$ 8c regpair-probe.c
 == naddr ==
REGPAIR <11> VLONG regpair-probe.c:181
   REGISTER R9 <11> LONG <eof>
   REGISTER R10 <11> ULONG <eof>
   (twice, then)
regpair-probe.c:181 bad in naddr: REGPAIR
```

**The `prtree` works and the shape is unremarkable** — an ordinary
VLONG register pair, R9/R10, reaching a function that can only take an

**And only 181 is named, so cases 12, 13 and 14 all compile.** That
kills hypothesis B as thoroughly as case 7 killed A:

- **case 14 is `s->size = d->offset`** — *the same two types as case 1,
  merely reversed* — and it compiles. So "the two structs are different
  types" is not the discriminator either.

***And cases 12–14 each varied THREE things from case 1*** — tag,
layout and member name. That is the exact fault named one paragraph
above them in this file. *Writing the rule down did not stop me
repeating it.*

What they do establish, with 4, 6, 10 and 11, is how narrow this is:

| | | |
|---|---|---|
| `d->offset = s->size` | case 1 | **FAILS** |
| `s->size = d->offset` | case 14 | passes — *same two types* |
| `gdst = s->size` | case 10 | passes — *same source* |
| `d->offset = gsrc` | case 11 | passes — *same destination* |

**`Src.size` loads fine. `Dst.offset` stores fine. Only the two

### Case 15 passes, and the probe has run out

`Named` is `Plain` with the member renamed `size`, and it compiles. So
**the member name is innocent too.** (And the run was verified with a
`grep` for `case15` in the file before being believed — *"looked
exactly like before" is also what a file that never got saved looks
like*.)

Three hypotheses dead: register pressure, the two types differing, and
the member name. What is left of `Src` is its tag and its **position**.

***And there is a variable nobody has held constant, which the probe
imposed rather than tested: `case1` is the FIRST FUNCTION in the
translation unit, and every case that passes comes after it.*** No case
added to that file could ever show this, because every one of them was
added to the same file.

### `regpair-min.c` — the whole question in one function

The probe grew to fifteen cases and 450 lines while the thing it asks
about is three lines. So: case 1, and nothing else.

```

```

```
regpair-min.c:69 bad in naddr: REGPAIR
```

***IT FAILS.*** Two structs and one assignment reproduce it — no other

**And `cgen.c` is now cleared by reading as well**: its only

### Position is irrelevant: the fourth hypothesis is dead

```
8c regpair-min.c            -> regpair-min.c:101  bad in naddr: REGPAIR
8c -DLEADER regpair-min.c   -> regpair-min.c:101  bad in naddr: REGPAIR
```

**Both name 101, so both are the right file, and both fail.** A trivial
function ahead of `case1` changes nothing, so per-function backend

Four hypotheses killed by measurement — register pressure (case 7), the
two struct types differing (case 14), the member name (case 15),
position (`-DLEADER`) — and reading has cleared all five of APExp's 8c
deltas. **Everything points at the shared front end.**

### `sys/src/cmd/8cu` — the one build that settles it

Upstream 9front's `8c` sources, verbatim, linked against **APExp's**
`cc.a`:

```
cd sys/src/cmd/8cu && mk install
cd ../../../lib/tests && 8cu regpair-min.c
```

- **Fails** → the fault is in APExp's `cc/`, where every other line of
  evidence already points.
- **Passes** → the fault is in APExp's `8c/` after all, and the reading
  that cleared those five changes is wrong somewhere. *That would be
  worth more than a confirmation.*

`mkfile.port`'s `$LIB: $CCSRC` rule does `cd ../cc; mk install`, so the
`cc.a` it links is the current one rather than a stale copy — the point
of the experiment, not an accident.

**It needs no shim, and the earlier instruction to add one was wrong.**
I said upstream's `ginit` must gain `typecmplx = typesuv;` or `pgen.c`
would fault on the first function with a return value. `cc/sub.c`'s
`tinit()` already sets it among the 32-bit defaults; every backend's
copy is redundant. *Following that instruction would have meant editing
a vendored file for no reason and then wondering whether the edit
mattered.*

**Deliberately not in `sys/src/cmd/mkfile`'s `DIRS`**: one failing
entry aborts the whole tree's `mk`, and these sources have never been
compiled here. The first build is the VM's. If it does not compile,
*that is informative too* — it would mean upstream's backend has moved
past our front end in some way the diff did not show.

The mkfile differs from upstream's in three ways and no more: `TARG=8cu`,
this tree's `APEXPROOT`/`mkone` idiom, and `OFILES` dropping
`8c_vla.$O`. Delete the whole directory once it has answered.

### FIXED, AND MEASURED

```
bash-5.3$ 8c regpair-min.c
bash-5.3$ ls -l regpair-min.*
-rw-rw-r-- 1 glenda glenda   813 regpair-min.8
```

**`regpair-min.8` where there were two diagnostics.** The cause was
`typesuvinit[]` losing `TVLONG` and `TUVLONG` — `8c/cgen.c` opens with
`if(typesuv[...]) sugen()`, so a 64-bit value stopped being treated as
a memory object and fell into the register path, where it is a pair,
and a pair reaches `naddr`, which can only take an address.

**And `objtype=386 mk install` is now past `sys/src/cmd` entirely** —
every compiler, assembler and linker builds for 386 — and into
`sys/src/ape/lib/ap`.

*The hunt cost eleven rounds and the fix is two words in an array.* What
it bought besides the fix: `8cu`, `regpair-min.c`, `regpair-probe.c`,
the `prtree` in `naddr`, four upstream backports, and a dated fork
point. **The expensive part was never the fix; it was getting to a
question that could be answered in one compile.**

9c override `typecmplx = typesu` and the other seven take `tinit`'s
`typesuv`. APExp's `typesuv` is now that list plus `TCFLOAT`/
`TCDOUBLE`, and `typesuc` is upstream's `typesu` plus the same two.
*Every backend's `typecmplx` membership matches upstream's for every
type upstream has.* So a failure that survives this is upstream's
own 32-bit limit or one of APExp's other deltas, and not this.

**The sharpest consequence is on the RETURN path, and it is not the
one the fix was aimed at.** `cc/pgen.c` tests `typecmplx` three times
to decide whether a function's return value needs a hidden `.ret`
pointer. With `TVLONG` missing, a vlong return on a 32-bit backend
took neither the `.ret` arm nor — for 5c, which does not set
`newvlongcode` — the `regret` arm below it. **5c and qc are recorded
as failing on exactly that: RETURNING a vlong**, which 8c compiled.
*That is a second symptom of the one cause, and nothing at the time
connected them.*

**Prediction, with its refutation condition:**

- **8c** (386) compiles `regpair-min.c` and the whole probe. *Already
  measured for `regpair-min`; the probe is the untested half.*
- **5c** (arm) and **qc** (power) now compile the probe, the vlong
  return included. **Refuted if either still fails on case 2.** This
  is the prediction with something to lose: it says two failures
  recorded as separate pieces of work were one.
- **kc** (sparc64) and **vc** (mips) still compile it. kc already did;
  vc was never in the recorded split and is the one unknown among the
  passes. **Refuted if either now fails** — which would mean the fix
  moved a backend from working to broken, and matters more than any
  pass here.
- **1c** (68000) and **2c** (68020) **still fail**, and this is the
  half the fix is NOT predicted to carry. They answered `GOK in
  gopcode: AS` on every case including ones with no vlong in them,
  which reads as no 64-bit support in those backends at all rather
  than as a front-end predicate. **Refuted if either compiles** — a
  welcome refutation, and it would mean "no vlong support" was a
  summary of this one bug after all.

**The run is two commands per backend and nothing has to be rebuilt
for it**, since the compilers were all rebuilt for the `typesuv` fix:

```
cd sys/lib/tests
for(c in 1c 2c 5c 6c 7c 8c 9c kc qc vc) { echo '== '^$c; $c regpair-min.c }
for(c in 1c 2c 5c 6c 7c 8c 9c kc qc vc) { echo '== '^$c; $c regpair-probe.c }

*(`for` and `^` because this is rc; `$c regpair-min.c` with a bare `=`

### The kc/vc fault is upstream's, and the fix only stopped masking it

`d->offset = v` has type `vlong`, so `cgen` sends it to `sugen`, which
falls through `default:` to `copy:` and calls `reglcgen` on the

addressable. *Which is the same shape as the 8c bug read from the other
end: a value the front end does not consider a memory object, handed to
a path that assumes one.*

**But only two backends fail, and the discriminator is a way out of
`copy:` for a 64-bit value:**

| cc | `cgen` sends vlong to `sugen`? | way out of `copy:` | case 3 |
|---|---|---|---|
| 1c, 2c | yes | older `sugen(n, result, nn, w)` | compiles |
| 5c | yes | `cgen64()` in `cgen.c` | compiles |
| 8c | yes | `cgen64()` in `cgen64.c` | compiles |
| kc, vc | yes | **none** | **fails** |
| 6c, 7c, 9c, qc | no — never dispatches | n/a | compiles |

**And it is upstream's.** `diff` against 9front HEAD:
`kc/cgen.c` and `vc/cgen.c` differ from upstream by **`OALLOCA` and
the `true` → `cond` rename and nothing else** — 97 and 100 diff lines,
every one of them in those two changes. The `typesuv` dispatch at
line 20, `sugen`, `copy:` and `lcgen` are upstream's verbatim, and
**upstream's `typesuvinit[]` carries `TVLONG`** exactly as ours does
again. *So upstream's own kc and vc fail on this, and what our fix did
was stop hiding it.* The emptied table that broke 8c was, on these two,
masking a different gap.

***That is this tree's own rule about a fix exposing new ground,
applied to a compiler instead of a process*** — and it is the reason
the refutation condition was worth writing down in the form it was.
"The fix moved a backend from working to broken" was the right thing
to watch for and the wrong description of what happened: kc was never
working, it was never asked.

**Not fixed, and that is a decision rather than a deferral.** kc and vc
are sparc64 and mips; nothing in this tree builds for either, the fix
is in code generation for instruction sets there is no way to test
against here, and 0.7's cross item is 386 first. It goes in 0.6's
open-bug inventory with the mechanism, which is what that list is for.
*A recorded diagnosis for an untestable target beats a plausible patch
for one.*

### Third blocker: `8a fenv.s`, and it is the widest finding yet

```
8a	fenv.s
fenv.s:10 syntax error, last name: .Lnum1_0
	line:	LNAME.: $$5 line
	inst:	LNAME.= expr
	saw	LNAME
fenv.s:12 syntax error, last name: b
	nam:	LNAME offset.( pointer )
fenv.s:14 syntax error, last name: DX
	rimrem:	rim ,,rem
	saw	$
	... too many errors
```

**Read `saw`, not `last name`, and the `.` is yacc's item dot.** It
marks the parse position inside the production, not a character in the
file — so `inst: LNAME .= expr` means "saw an LNAME, wanted `=`", and
the token that actually broke is the one under `saw`. *Two of the three
diagnostics name an innocent token in their `last name` field.*

**Three `as` bugs, each stated against 8a's own grammar:**

1. ***`CALLL` and `JMPL`*** — the GAS operand-size suffix appended to
   **control transfers**. `8a/lex.c` has `CALL`, `JMP`, `JMPF` and no
   suffixed forms, so `CALLL` lexes as an ordinary name and the parser
   then wants `:` or `=`. (lines 10, 45, 80, 111, 148)
2. ***GAS numeric local labels passed through verbatim*** —
   `ADDL $__hwcap-1b, (SP)`. `1b` is GAS for "the nearest `1:` above";
   8a lexes the number 1 and then a name `b`. (lines 12, 82, 113, 149,
   171)
3. ***TEST's operands reversed.*** `a.y` has `rimrem: rim ',' rem`,
   `rim: rem | imm`, `rem: reg | mem` — **an immediate is legal as the
   first operand and illegal as the second**. `TESTL (DX), $0x02000000`
   and `TESTL AX, $0x3f` are both that one error, and the diagnostic
   prints the production verbatim. (lines 14, 42, 84, 115)

***And fixing all three would leave the file useless, which is how the
real finding turned up.*** `__hwcap` **exists nowhere in libap**: the
only five references in the whole tree are the five lines in this file.
musl's i386 `fenv.s` reads it at run time to choose between the MXCSR
and x87 paths, and the PIC sequence those `CALLL`/`1b` lines implement
exists only to address it. *So the source cannot be translated into
anything that works here, however good the translator gets.*

**Which prompted asking what the other five were doing — and the answer
is nothing.** `grep -c '^TEXT'` over all six `arch/*/fenv.s` is **0**.
`as` rendered `.globl name` and `.type name,@function` as COMMENTS and
emitted `name:`, and `8a/a.y`'s `line: LNAME ':'` sets `type = LLAB`
and `value = pc`: **a bare label is an assembler-internal address, not
a symbol.** Only `TEXT`, `GLOBL` and `DATA` reach the object file.

***So the fenv API has been a stub on every architecture, amd64
included.*** What answers `feclearexcept`, `fetestexcept`,
`fegetround`, `fesetround`, `fegetenv` and `fesetenv` is
`lib/ap/fenv/fenv.c` — **musl's fallback for "archs lacking fenv
implementation", which says exactly that in its own comment** — and it
returns 0 or `FE_TONEAREST` to everything. In musl the arch file is
built *instead of* that one; here both were, and the one with symbols
won. **The stub-answers-the-wrong-thing family, and the widest instance
in this tree**: `fetestexcept()` reports no exception ever raised and
`fesetround()` silently does nothing, in every APE program there has
ever been here.

**`fenv.$O` is out of all six arch mkfiles**, which unblocks 386 and
**cannot change behaviour anywhere**, by construction: removing an
object that defines no symbols cannot change a link. Each file keeps a
banner saying what it is and why it is not built. *The FP environment
itself is unaffected* — that is `arch/$objtype/main9.s`, which is a
real `TEXT` file on the startup path, **and the invariant in
`CLAUDE.md` had been crediting `fenv.s` for `main9.s`'s MXCSR load.**
One wrong filename in a note, pointing at the one file in the pair that
does nothing.

**Writing real ones is per-architecture work and is not in this round.**
`arch/386/getfcr.s` is the shape to follow, and the 386 version is the
x87-only path — there is no `__hwcap` to ask.

*Three blockers in, and the shape has held every time: nothing has
built 386 since the musl reorganisation, so what 386 finds is whatever
stopped being true for everyone and was only ever checked on amd64.*
**The difference this time is that the fault was not 386's.**

runtime.c:3423[stdin:12686] unknown op in cgen: CONST
runtime.c:3455[stdin:12718] unknown op in cgen: CONST

***And `C_word` is `int64_t` here, on a 32-bit machine, because this

**The same flags are in `cmd/chicken/mkfile` too**, with the same
comment copied, and would have stopped the build two directories
later. Both are fixed.

#### The prediction, and what refutes it

*Fixing a configuration can make a diagnostic disappear without
anyone having diagnosed it*, which is this tree's
two-changes-and-the-wrong-one-gets-the-credit trap arriving in
advance. So:

**Predicted**: `runtime.c` compiles. With the flags gone on 386,
`C_word` is `int`, `C_SCHEME_UNDEFINED` is an ordinary 32-bit
constant, and the OCONST that reached `cgen`'s default arm is not
64-bit any more.

**Refuted if** the three `C_debugger(&cell, 0, NULL)` lines still
answer `unknown op in cgen: CONST`. Then the flags were innocent, 8c
has a real gap on a constant that `addable >= INDEXED` does not cover,
and the mkfile change stands anyway on its own terms — *an ILP32
target must not be told it is LLP64 whatever else is true.*

**Either way the next occurrence will name its own shape**, because
`8c/cgen.c`'s default arm now carries `prtree(n, "cgen")` beside the
diagnostic, the same unconditional idiom as `naddr`'s in `txt.c` and

#### One wart found beside it, left alone, and why

`apexp-cpu-caps.c` defines `crypto_cpu_caps_amd64` by that name, while
i386's header declares `crypto_cpu_caps_i386`. So on 386 the stand-in
defines a name nothing declares and leaves a declared name undefined.

target.

### Seventh blocker: `$objtype` where `$cputype` was meant

```
../../../../../386/bin/pcc -o 8.out shell.8 eval.8 parse.8 ...
/rc/lib/rcmain:24 *eval*:1: .../386/bin/pcc: exec header invalid
```

**A 386 binary handed to an amd64 kernel.** `cmd/bash/mkfile:102` had
`LD=$APEXPROOT/$objtype/bin/pcc`.

***This is the distinction the whole cross item was predicted to
surface, arriving in its purest form.*** The comment above that line
is right — "the system pcc may predate patches that bash needs, use
the APExp-local pcc that just got rebuilt" — and the variable was
wrong. **A compiler is RUN on `$cputype`; only its output is FOR
`$objtype`.** On a native build the two strings are equal, so nothing
could ever have shown it. *Fourth instance of that shape in this item,
after `mount-include`, chicken's word-size flags and LibreSSL's arch
directory.*

**The sweep separated the real hits from the innocent majority**, and
the majority is large: `$objtype/bin` appears in about ninety mkfiles
and **almost all of them are `BIN=`, the install DESTINATION, which
correctly takes `$objtype`.** Two kinds are genuinely different:

- **Executed** → the host's. `bash/mkfile`'s `LD`, and in
  `objc/mkfile.rebuild` the `sh` in `$OBJC`, `OBJCBIN` (which points
  the driver at the stage 1 compiler), `$YACC` and `$LEX`.
- **Read, linked or installed** → `$objtype`, and these were already
  right: every `BIN=`, `OBJCLIB`, `OBJCINC`, and
  `cmd/pax/mkfile:189`'s `PAX_SAFE_PATH` — *a path the finished binary
  uses on the target machine, which is `$objtype` precisely because it
  is not this build's to run.*

#### And four of the five want no path at all

The first fix here was `$objtype` → `$cputype`, which is correct and
is **not what those lines should say**. *The absolute paths are
residue from early APExp*, when nothing stopped the HOST's `pcc`,
`bison` or `flex` answering first, and **the union mounts have since
made that impossible**: `apexp-sh` binds `$cputype/bin` and
`$cputype/bin/ape` over `/bin` and **sets `LD=pcc` itself**, so a bare
name is already this tree's own.

So `LD=pcc`, `YACC=bison`, `LEX=flex`, `OBJC=sh …` — *a bare name has
no architecture in it to get wrong*, which is a stronger guarantee
than spelling the right one. `CC=pcc` on the line above bash's `LD`
had been doing exactly this all along, which is the tell that the path
was never load-bearing.

**`OBJCBIN` keeps a path**, and the distinction is worth stating: the
driver reads it as a **directory** to find stage 1's `objc1` in, not
as a command to look up. So it is `$cputype`, because `objc1` runs.

*The `$cputype`/`$objtype` rule stands and is still what `OBJCBIN`
turns on; it just is not the shortest fix for the other four.*

ASN1_TIME_adj_internal: undefined: OPENSSL_gmtime_adj
ASN1_TIME_diff: undefined: OPENSSL_gmtime_diff
x509_verify_asn1_time_to_time_t: undefined: asn1_time_tm_to_time_t
```

**All four are defined in one file**, `crypto/asn1/a_time_posix.c` —
lines 226, 249, 275 and 207 — and `a_time_posix.$O` **is** in the
mkfile's `OFILES` (line 66). So this is not four problems: it is one
object missing from the 386 archive.

***And that object is exactly the file the libressl blocker died
on.*** The diagnostic two rounds ago was
`crypto/asn1/a_time_posix.c:33 Could not find include file
"crypto_arch.h"`.

#### Why an interrupted build can lose an object, and the one thing
#### that would settle which mechanism it was

`sys/src/cmd/mksyslib` is

```
$LIB:V:	$OFILES			# force archive even when not needed
	ar vu $LIB $newprereq
```

**`$newprereq` is what THIS RUN rebuilt.** An object left on disk by
an earlier run is up to date, so it is not a new prerequisite, so
`ar vu` never names it — *an archive assembled across two runs can be
missing whatever the first run built.*

**But that mechanism predicts MANY missing objects and we see one**,
which is the discriminator doing its job before a round was spent on
it. Two candidates remain and they are told apart by one command:

```
ar t $APEXPROOT/386/lib/ape/libressl.a | grep a_time_posix
ls -l sys/src/ape/lib/libressl/a_time_posix.8
```

- **Absent from the archive, no `.8` on disk** → the `$newprereq`
  mechanism above, and the lesson is about resuming interrupted
  builds.
- **Present in the archive, or a `.8` that exists and is tiny** → the
  failed compile left an output file NEWER than its source, mk called
  it up to date on the next run, and `ar` archived something with no
  symbols in it. *That is the same family as "a measurement of a build
  that does not contain the change measures nothing", one level down
  — and it fits the single-object observation exactly.*

**The mechanism is deliberately NOT written into `CLAUDE.md`'s build
rules yet**, because it has not been measured and the two candidates
carry different lessons. One `ar t` decides it.

#### The fix either way

`mk nuke` in `sys/src/ape/lib/libressl` removes `*.[$OS]` and `$LIB`,
and **it is bounded here**: that mkfile assigns `APEXPROOT` as the
literal `../../../../..` on its first line, so `$LIB` is this
repository's own `386/lib/ape/libressl.a` and cannot expand to the
host's. (The warning in `CLAUDE.md` is about an EMPTY `$APEXPROOT`,
which takes a command-line override to produce.) Then
`objtype=386 mk install` in that directory, and on up.

*Nothing in the tree was changed for this one* — it is a stale build
artefact rather than a source fault, and the round's value is the
`ar t` that says which kind.

### Ninth blocker: bash builds a tool for the target and then runs it

A cleanup and rebuild moved the stop to bash:

```
mk: mkdir -p builtins ... : exit status=rc: exec header invalid
/rc/lib/rcmain:24 *eval*:2: ../../mkbuiltins: exec header invalid
```

**Not a path problem** — `../../mkbuiltins` is relative and correct.
`mkbuiltins` is bash's own code generator: it reads the forty-three
`.def` files and writes `builtext.h`, `builtins.c` and one `.c` per
builtin. The rule that builds it was

```
$MKBUILTINS: $BASHSRC/builtins/mkbuiltins.c
	pcc -I$BASHSRC -I$BASHSRC/include -o $target $prereq
```

and a bare `pcc` reads `$objtype`, so **it built the generator FOR
386** and the next recipe ran it.

***And the comment directly above that rule has always said
"mkbuiltins is a build-time helper: compile it with the HOST cc, not
with our cross pcc".*** *A file that states the rule and then does not
follow it, for the fourth time in this walk* — after LibreSSL's arch
names, chicken's word-size flags and bash's own `LD`. On a native
build `$objtype` and `$cputype` are the same string, so not one of the
four could have been shown by the build being run.

The fix is `objtype=$cputype pcc …` on that one compile. **The leading
assignment is legal rc** — an assignment in front of a command is
local to it, the same form as the `objtype=386 mk install` that found
this — whereas an assignment used as an ARGUMENT, `mk
objtype=$objtype install`, is the parse error `rceq-sweep.py` gates
on. *The two look alike and only one works*, which is why the sweep
exists.

#### And it splits the self-run list in two

`cmd/perl/mkfile:86` (`./miniperl`), `cmd/muon/mkfile:192`
(`./embedder`) and `cmd/objc` were recorded as "recipes that run a
binary they just built", and `mkbuiltins` looked like a fourth. **It
is not the same thing.**

- **A build-time helper** produces source and contributes nothing to
  the product. It can simply be built for the host, and one leading
  assignment is the entire fix. `mkbuiltins` is this.
- **A bootstrap stage** runs the product itself — `miniperl` *is*
  perl, `objc1` *is* objc — so building it for the host means building
  the port twice, which is a different and much larger piece of work.

*So the list of ports that genuinely cannot cross-compile is three,
not four, and the question to ask of the next one is which kind it
is.*

### Making it a rule: `hostcc`, and the half that is not the compiler

One leading assignment fixes bash. **Making it a rule the next helper
inherits took three pieces, and only the first is the obvious one.**

**1. `rc/bin/ape/hostcc`** — one line of rc, `objtype=$cputype` then
`exec pcc $*`, beside `c89`'s existing `exec /$cputype/bin/ape/cc $*`.
*A command rather than a `HOSTCC=objtype=$cputype pcc` variable*, for
two reasons that are both about the `=`: **a variable holding an
assignment is invisible to `rceq-sweep.py`**, which reads the mkfile
text and not what mk expands it to; and an assignment is legal only
LEADING, so such a variable used anywhere but the start of a recipe
line is a parse error in a mkfile that reads fine.

***2. `mount-include`, and this is the half that makes it correct
rather than apparently correct.*** Every bind there is for `$objtype`
— including `bind -b $objtype/include/ape /sys/include/ape`. So during
a cross build nothing puts APExp's HOST headers where a host compile
looks: `/$cputype/include/ape` is **stock 9front's**, and
`/sys/include/ape` carries the TARGET's arch headers. A `hostcc`
compile on an amd64 machine building for 386 would have picked up
**386's `stddef_arch.h`**, whose `_ptrdiff_t` is `long` — 32-bit —
and *nothing in any message would have said so.* It now binds
`$cputype/include/ape` and `$cputype/lib/ape` when the two differ, and
**the header-order invariant is what makes that enough**:
`/$objtype/include/ape` is searched ahead of `/sys/include/ape`, so
the host's twelve arch headers come first for an `objtype=$cputype`
compile. *The compiler invocation was the easy half.*

**3. `sys/lib/tests/hosthelper-sweep.py`** — which mkfile recipes run
a binary the same mkfile builds, and was it built with `hostcc`.
**It does NOT gate, on purpose**: a `no` is a question, because a
build-time helper should use `hostcc` and a bootstrap stage cannot, so
a gate would demand a change that must not be made.

```
mkfile                                 line   runs           hostcc?
sys/src/ape/cmd/bash/mkfile            281    mkbuiltins     yes
sys/src/ape/cmd/muon/mkfile            192    embedder       no
sys/src/ape/cmd/perl/mkfile            86     miniperl       no
sys/src/external/f2c/src/mkfile.plan9  104    xsum           no
```

***Its first run missed its own positive control***, printing the
three `no`s and not bash at all: it expanded `NAME=./thing` aliases in
recipe lines but not in target lines, and bash's rule is
`$MKBUILTINS:` — *the recipe matched, the rule did not, and the pair
never met.* **The only reason that was caught is that the sweep was
run against a case whose answer was already known.** Breaking `hostcc`
back to `pcc` flips bash's column to `no` and restoring it flips it
back, which is the control a sweep in this tree is supposed to have.

**`xsum` is a hit and not a live one**, checked once and written down
so nobody checks again: `external/f2c/src/mkfile.plan9` builds it and
runs it from an `xsum.out` target, and **nothing in this tree includes
that mkfile** — `cmd/f2c/mkfile` compiles f2c from `$F2CSRC/src/%.c`
with its own rules, and the only occurrences of the name
`mkfile.plan9` anywhere are inside f2c's own source listings. *An
untriggered rule gets no diagnostic from anyone*, for the third time
in these notes, and editing upstream's dead makefile would buy
nothing.

**`objc` does not appear and that is a known blind spot**: its stage 1
is in `mkfile` and the stage that runs it is in `mkfile.rebuild`, and
the sweep looks within one file. Said in its header rather than left
for a clean run to be misread.

#### objc is corrected and still cannot cross-compile

Saying both is the point. objc's stage 1 builds `objc1` **for the
target** and stage 2 **runs it**, so it joins `cmd/perl/mkfile:86`
(`./miniperl`) and `cmd/muon/mkfile:192` (`./embedder`) on the list of
recipes that run a binary they just built — **three now, not two.**
The variables were corrected because they were wrong, not because
correcting them is sufficient, and `CLAUDE.md` now says so at the
point that list is kept.

*bash's fix, by contrast, is complete*: `pcc` on the host driving
`8c`/`8l` is exactly how every other directory in this walk has been
building.

### Upstream's history, and the attribution settled

`git://git.9front.org` is blocked from the build host, but
**`https://github.com/9front/9front` is reachable**, and a blobless
sparse clone of `sys/src/cmd/cc` and `sys/src/cmd/8c` answers what the
`diff -r` could not.

**The `nodrat` → `regsalloc` change is upstream's:**

```
ed3c7d491  2025-12-27  cinap_lenrek
    ?c: eliminate .rathole for arm, arm64, 386, arm-thumb and mips
```

**and APExp has it** — APExp's `8c` is identical to upstream HEAD on
that hunk. ***So "stock 8c compiles it" means "9front from before
December 2025 compiles it"***, not "an unmodified compiler does".

**APExp's kencc base is now dated**: it carries `3ea08ad83`
(2025-12-28, *grow regions dynamically* — we changed only the initial
constant, 300 → 600) and lacks `a68335214` (2026-06-10, *untangle class
and type specifiers*, which is where `struct Spec` comes from). Fork
point between those two dates.

**APExp's entire 8c delta from upstream HEAD**: `OALLOCA` (VLA), the
`true` → `cond` rename, complex and VLA bits in `txt.c`, `-J` in
`swt.c` (gated on `conformalign`), and `maxregion` 300 → 600 in
`reg.c`. `cgen64.c` differs by **the rename alone**, so we carry
`f4c733880` (2025-09-23, *use hint for register pair*) untouched —
which matters, since it is upstream's most recent work on REGPAIR
itself.

### Two machines, and the diffs came from the wrong one

The tree the `diff -r` was taken from has `struct Spec` (June 2026) in
`cc/cc.h` **and** `nodrat` (removed December 2025) in `8c/cgen.c`.
Upstream has `Spec`, has no `nodrat`, and never reverted, so **no
single 9front checkout can be in that state.**

**The cause is known**: that is the development VM and *its `sysupdate`
is broken*. It is the machine used because GitHub authentication works
there, and normally that costs nothing, because nothing in this project
touches the underlying system — but a `diff -r` against `/sys/src` is
exactly a thing that does.

***So `tmp/cc.diff` and `tmp/8c.diff` are void as statements about
stock.*** They compared APExp against a tree that is part 2025 and part
2026. *Taking them was right; reading them as a patch set was not* —
the same error in a third costume. The upstream clone replaces them,
and every attribution above rests on that instead.

**The compiler measurements are from a different, clean machine and
they stand**: a second VM on completely clean source is where stock
`8c` compiled `ar.c` and `regpair-probe.c`, and where all of
`/sys/src` cross compiled to 386. It can download but not push, which
is why the diffs came from the other one.

### So the live question is two greps wide

**What vintage is the clean VM?** Its `8c` is the one that compiles the
probe, and whether it carries `ed3c7d491` decides the rest:

```
grep -c nodrat /sys/src/cmd/8c/cgen.c     # 0 = has the rathole change
grep -c Spec /sys/src/cmd/cc/cc.h         # 0 = predates 2026-06-10
```

- **`nodrat` 0** → the clean VM is post-December-2025 and agrees with
  APExp on that hunk. ***Then the rathole change is exonerated and the
  fault is one of APExp's five deltas*** — and only `maxregion`
  300 → 600 and the `CLOCAL` class test are neither gated nor inert.
  That would be a one-line revert away from an answer.
- **nonzero** → the clean VM predates it, and `ed3c7d491` or something
  after it is still the suspect.

*Two greps bracket that compiler's vintage the way the clone bracketed
APExp's, and the second is not redundant: it says whether the bracket
is the same one.*

### The decisive test

**Build upstream 9front HEAD's `8c`, unmodified, and run it on
`regpair-probe.c`** — and the clean VM can do that with no GitHub
credential at all, since `git/clone https://github.com/9front/9front`
only downloads.

- **Fails** → the bug is upstream's, in or after `ed3c7d491`, and we
  merely have it. That is a 9front bug report with a three-line
  reproduction attached, and we can carry a local fix meanwhile.
- **Passes** → it is one of our five, and only `maxregion` and the
  `CLOCAL` test are neither gated nor obviously inert.

Either way the `prtree` now in `naddr` prints the shape on the failing
side, so the next round has a tree rather than a message.

### The shape to expect after that

**A recipe that runs a binary it just built cannot cross-compile**, and
the tree has two outside `mk test`: `cmd/perl/mkfile:86` (`./miniperl`
generates `perlmain.c`) and `cmd/muon/mkfile:192` (`./embedder`). Each
needs a host build of that one tool, or a checked-in generated file.
libressl's `test/mkfile` runs several, but only under `mk test`.

## 4. portable_stl

**Both questions are answered from the source, and both answers are
no.**

### There is nothing to build and nothing to install

`CMakeLists.txt` has **no `install()` rule and no `configure_file`**.
Its single target is `add_executable(portable_stl unit_test/...)` — the
gtest suite — and it fetches Hunter and GTest from the network to build
it. So "nothing changes in the headers" is exactly right: *the headers
are the product.* `cmake .. && make` builds the test binary and nothing
else.

**So installation is a copy**, and `sys/include/ape/pstl` is a
reasonable home. The one thing to decide is whether anything in the
tree should see it without asking — it should not, which an
`-I$APEXPROOT/sys/include/ape/pstl` in the consuming mkfile gives and a
default search path does not.

### The namespace cannot become `std`, and `portable_stl` is not just
### conflict avoidance

`namespace portable_stl` is spelled out **1283 times** across the
headers, with nested helper namespaces inside it, so it is not a single
`#define` point. That is the weak reason. The strong one:

> `include/portable_stl/language_support/initializer_list_stl/initializer_list.h:15`
> `namespace std {`
> `include/portable_stl/language_support/typeinfo/type_info_stl/type_info.h:18`
> `namespace std {`

**The library already uses `namespace std` itself**, for the two things
the *core language* requires to live there: `std::initializer_list`,
which every braced-init-list resolves against, and `std::type_info`,
which `typeid` returns. A `namespace std = portable_stl;` would collide
head-on with its own declarations. *`std::` is not free here; it is
occupied on purpose.*

**And renaming would not buy compatibility anyway**, which is the part
worth stating plainly rather than discovering in a port:

```cpp
::portable_stl::expected<void, ::portable_stl::portable_stl_error>
push_back(const_reference value);
```

`vector::push_back` returns `expected<void, portable_stl_error>`, not
`void`. **The library is exception-free by construction** — that is what
it is *for*, which is also why it suits a toolchain with no exception
runtime — so every fallible operation returns `expected`. Code written
against the real `<vector>` does not compile against it whatever the
namespace is called. ***It is a conformance corpus and a usable library,
but it is not a drop-in `std`.***

## 5. A proof-of-concept C++ application

Two candidates, and they ask different questions:

- **a modern unrar** — C++ since 2.71, which is why the tree ships the
  last pure-C version. It would be the first real test of the EDG
  pipeline on somebody else's C++, and it needs an STL.
- **tkdesk** — its mkfile is in `sys/src/ape/app` and it is **not built
  by default**, being a proof of concept rather than part of APExp. It
  is C, so it proves itcl/Tk rather than C++; the bonus is that it is
  the first real itcl/Tk application here. (`tkblt` was dropped: 3.2 is
  C++ with namespaces, and tkdesk never needed it — it ships its own BLT
  subset in C.)

**What the C++ one has to clear first** is in `docs/notes/edg.md`: the
static-init gap (nothing calls `_Z12__call_ctorsv`), `__thread` silently
dropped, and `--instantiate local`'s own cost — internal linkage gives
each object its own copy, so a template's static data member stops being
one object shared across the program. *A program whose correctness rests
on that identity is silently wrong rather than loudly broken, and one
translation unit cannot show it.*
